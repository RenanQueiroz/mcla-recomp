# Video memory above native resolution (fork issue #19), 2026-10-28

Report (iDexPro, 2026-10-28): Acer Nitro 5, i7-12700H, RTX 3060 laptop (6 GB), 32 GB RAM. At native 720p with CAS upscaling the game runs at 80 to 90 FPS even in crowded city
areas. At 2x resolution it runs 50 to 60 FPS for about 20 seconds, then drops to about 5 FPS; opening the pause menu drops it at once.

**State: the fixes are written, compiled by CI and measured on one machine (RTX 5080, D3D12 at 1x, 2x, 3x and Vulkan at 1x, 2x, 3x for the released v0.2.0; D3D12 at 2x with the fixes; section 6). Not run when this was written: 3x and Vulkan with the fixes, a card with 6 GB, the pressure response (it never triggered). ## 1. What the SDK and the fork allocate on the GPU (read), and how it scales

`s` is `resolution_scale` (1, 2, 3). The SDK is v0.10.0 with the fork's patches (the scratch copy of the SDK source used for this reading had `patches/` applied by `git apply`).

| Resource | Size | Scales with | Grows over time | Where (read) |
|---|---|---|---|---|
| EDRAM buffer (the host copy of the console's 10 MB eDRAM) | `edram_tiles` x 80 x 16 x 4 B x s^2 = 20 MiB x s^2 at the fork's 4,096 tiles (20 / 80 / 180 MiB at 1x / 2x / 3x); 2,048 tiles halves it | s^2 | no | `d3d12/render_target_cache.cpp:473` (a committed buffer), `edram-size` patch |
| Host render targets | one committed resource (D3D12) or one image with its own `VkDeviceMemory` (Vulkan) per key (EDRAM base, pitch in tiles, MSAA, format, colour or depth). Size = width x s, by **tile_rows x (16 >> msaa_y_log2) x s** rows, x samples x bytes a sample. tile_rows = 2,048 / pitch tiles, clamped so the height is at most 8,192 x s and the host's maximum (D3D12: 16,384). 2,048 is the console's EDRAM whatever `edram_tiles` is: a render target is as tall as the whole EDRAM from its base. So a key costs about **10.5 MB x bytes a sample x s^2** whatever it draws (4 B: 32-bit colour, D24S8; 8 B: the HDR scene colour R16G16B16A16_FLOAT and D24FS8 = R32G8X24) | s^2 x number of keys | **yes: made on first use, never freed** (`RenderTargetCache::ClearCache`, which frees the ones owning no EDRAM range, runs only on the debug request to clear the caches) | `pipeline/render_target/cache.cpp` `GetRenderTargetHeight`, `d3d12/render_target_cache.cpp:2054`, `vulkan/render_target_cache.cpp:2738` |
| Scaled resolve buffer: with `s` > 1 a resolve writes only this, and a texture made from resolved memory loads from it | virtual 512 MB x s^2 (2 GB at 2x, 4.5 GB at 3x: address space), committed in **16 MB heaps** (D3D12 `CreateHeap` + `UpdateTileMappings`) or sparse binds (Vulkan: 4 MB at 2x, 8 MB at 3x); a heap covers 16 / s^2 MB of guest memory, so each distinct 4 MB (2x) or 1.8 MB (3x) block of guest memory resolved to costs one heap. Without Vulkan `sparseResidencyBuffer` the whole 2 GB / 4.5 GB is one dedicated buffer | s^2 x distinct blocks | yes, monotonic; heaps never released | `d3d12/texture_cache.cpp:1175-1260`, `vulkan/texture_cache.cpp:2447` |
| Shared memory (the GPU's mirror of guest memory: vertex data, index data, texture sources) | virtual 512 MB, sparse 4 MB allocations (D3D12 tiled buffer); the full 512 MB if tiled resources are off | no | yes, up to 512 MB, never released | `d3d12/shared_memory.cpp:40-110` |
| Texture cache | soft limit 384 MB + 24 MB x (s^2 - 1), hard limit 768 MB + the same (2x: 456 / 840 MB; 3x: 576 / 960 MB); a texture unused for 30 s goes over the soft limit, any unused one over the hard limit | weakly | bounded by the hard limit | `pipeline/texture/cache.cpp:262-330` |
| Scratch, readback and downscale buffers (D3D12) | the largest resolve read back (`readback_resolve_rules`: the vinyl rule), megabytes | s^2 | grows, never shrinks | `d3d12/command_processor.cpp:3675-3866` |
| The fork's single-tile surface cache (`src/render_perf.cpp`, the game's `BeginTiledRendering` array at 0x828393D8) | **no host memory**: 8 slots of the game's own surface descriptors (a colour surface pointer, its depth surface 8 slots on, its MSAA mode); the game hangs on a ninth key, so the hook leaves one slot free. What costs memory is the render target keys the surfaces produce: single tile puts the scene's 64-bit colour at EDRAM base 1472 (the two-tile layout had it at 1024) with the depth at 0, both 1280 wide at 2x MSAA, so single tile adds one key (84 MB at 2x, 189 MB at 3x, once). 4x MSAA surfaces (2 x 2,944 tiles) do not fit in 4,096 tiles, so the pause menu and the GPS map keep their three tiles | s^2 | once | `render_perf.cpp:58-112`, `frame-structure-2026-10-16.md` |
| The pause menu and the GPS map (the world drawn again at 4x MSAA in three tiles of 1280x256, 256 and 208 rows, a 4x 8888 UI target, a 960x640 2x panel) | new keys on first opening, e.g. 4x MSAA 64-bit colour and D24FS8 depth at pitch 32 tiles (84 MB each at 2x): about 300 MB at 2x, 700 MB at 3x | s^2 | once, then kept | computed from the key rule |
| FSR / TAA (PERFORMANCE > ANTI ALIASING = FSR), frame generation, HDR | off by default (MSAA is the default); FSR about 500 MB at 4K (AMD's figure in KNOWN-ISSUES), HDR about 200 MB at 3x | display size | on switch | `d3d12/temporal_aa.cpp`, KNOWN-ISSUES |
| Swap chain, guest output, gamma ramp, descriptors, pipelines | about 240 MB in total at the title with every pipeline created (`shader-prepare-2026-10-17.md`) | no | no | |

## 2. The host render targets of the game: a census from the frame logs (computed)

`vram-rtcensus.py` (this folder) rebuilds the keys from the D lines of a frame log (`RB_SURFACE_INFO`, `RB_COLOR_INFO`, `RB_DEPTH_INFO`, the colour write mask, the depth control) with the SDK's rule
(`pitch_tiles_at_32bpp = ceil((pitch << msaa_x_log2) / 80)`, the key = base, pitch, MSAA, storage format, colour or depth) and sizes each as `CreateRenderTarget` would. It counts a key if a draw
that writes to it is in the log, so it is an upper bound: a draw with a stale colour register is counted.

| Scene (2 frames of the frame log) | keys | all host render targets, 1x | 2x | 3x |
|---|---|---|---|---|
| city at dusk (`C:\mcv\dither\fl\fl_dusk_0.txt`) | 33 | 482 MB | 1,929 MB | 4,092 MB |
| city at night (`fl_night_0.txt`) | 40 | 552 MB | 2,208 MB | 4,721 MB |
| arcade race in the rain, 2x (`rain17\fl\p2d-d3d12-x2-gt\rain_0.txt`) | 54 | 862 MB | 3,448 MB | 7,000 MB |

**A check of the size rule against an earlier measurement** (KNOWN-ISSUES, "Single-tile rendering", switching): when the targets of the two-tile layout were first made in a session, video memory rose by 42 MB at 1x and by
360 MB at 3x. The census gives a 64-bit key (the scene colour, 2x MSAA, 1280 wide) 20.0 MB at 1x and 180.0 MB at 3x, so two such keys are 40 and 360 MB: the rule is right to within 5% at both scales (measured by
another session, not by this one). The same line's anti-aliasing-off figure (20 MB at 1x, 106 MB at 3x) does not fit it (9x would be 180 MB); not explained.

The keys are 128 to 1,280 pixels wide (the scene, the shadow cascades, the environment and reflection maps, the post chain from 640x360 down to 4x4, the minimap, particle targets), and
almost every one is 2,048 tiles tall in the host. The biggest surface the game draws is 736 rows (the single tile); the viewports and window scissors in the logs are 720 rows or less.
`vram-checkcap.py` checks it: of the 33 to 54 keys in each log, the ones whose draws carry an extent (a viewport or a window scissor: 23 of 33, 22 of 40, 27 of 54) need at most **720 rows**, within a 768-row cap
as well as 1,024; the others (screen-space draws with the viewport off, mostly small 4x targets) have no extent in a frame log, because the SDK finds it at run time by executing the vertex shader on the CPU
(`execute_unclipped_draw_vs_on_cpu`), so a log can't say; the game's own log line says if the cap ever cuts a draw (`a draw reaches row`). A cap on the host height would therefore cost nothing the game uses
(not proven for the keys without an extent), and the same census with the cap computed:

| cap on the height (pixels at 1x) | city dusk 2x | city night 2x | race 2x | city dusk 3x |
|---|---|---|---|---|
| none (the SDK) | 1,929 MB | 2,208 MB | 3,448 MB | 4,092 MB |
| 2,048 | 1,332 | 1,537 | 2,111 | 2,997 |
| 1,536 | 1,149 | 1,322 | 1,833 | 2,585 |
| 1,024 (the fork's PC default) | 929 | 1,056 | 1,481 | 2,090 |
| 768 | 697 | 792 | 1,111 | 1,567 |

(`vram-rtcensus.py` also prints the saving of "height classes", sizing each key to what its draws need; it needs the draw extents the SDK estimates, which a frame log only has in part.)

new render target keys and scaled resolve heaps filling up while nothing is given back; the pause menu adds about 300 MB at 2x at once. The peaks measured afterwards (section 6: 1.65 to 1.69 GB at 1x, 3.9 to 4.0 GB at 2x, 7.46 GB at 3x) are inside these ranges; the pause menu added 190 to 210 MB at 2x, not 300.

## 4. What was written (three SDK patches, `patches/README.md`)

- `rexglue-render-target-max-height.patch`: `render_target_max_height` (the fork's PC default 1,024).
- `rexglue-render-target-trim.patch`: `render_target_trim_seconds` (60): free the render targets that own no EDRAM range and have not been used for that long, at the end of a frame after a wait for the GPU.
- `rexglue-gpu-memory.patch`: `gpu_memory_log_ms` (a line a second: what the OS says the process uses, its budget, and what the emulation holds), `gpu_memory_pressure_percent` (90: unused render targets go at
  once, the texture cache's limits are halved), `gpu_memory_emulate_mb` (D3D12, development: a ballast so that a bigger card behaves like a smaller one).

Not done, and why: sizing the scaled resolve buffer to what is used (releasing a 16 MB heap whose data a texture may still load from needs the pages' scaled-resolve marks cleared with it: more risk than
the first measurement justifies; the log line says how big it is), right-sizing each render target to its draws (new height classes in the key: a change to every transfer and resolve path), the
guest's 8-slot surface cache (it holds no host memory).

## 5. The measurement chain (`SP\vram19\chain.ps1` of the session that wrote this; one exclusive hold of at most 45 minutes)

Every run is the same pad: boot, free roam, 60 seconds of driving (segments `roam_a`, `roam_b`, `roam_c`, 20 s each; no feedback, so where the car goes is only logged), the pause menu open 20 s, the GPS map 12 s;
windowed, uncapped, RTX 5080 (adapter 0), PresentMon for the frame times per segment, **Windows' GPU memory counters every 500 ms** (`GPU Process Memory` Dedicated / Shared / Local / Non Local Usage and Total
Committed of the game's process, `GPU Adapter Memory` of each adapter; `vram-sampler.py`, this folder: the numbers Task Manager shows, from the video memory manager, so a D3D12 and a Vulkan process are counted alike).
The fix exe also logs what the SDK holds once a second (`--gpu_memory_log_ms=1000`).

Arms: the released v0.2.0 exe at 1x, 2x, 3x on D3D12 and Vulkan; at 2x with `--mcla_single_tile=false` and with `--edram_tiles=2048`; the build of `perf/vram-budget` at 2x and 3x with the three fixes off and on;
at 2x with `--gpu_memory_emulate_mb` = 80% of the released game's measured peak, fixes off and on (the ballast squeezes the game as a smaller card would: does the cliff appear, and does the fix avoid it);
pictures with the cap off and on (fixed 1/60 s a frame: the city, the pause menu, the GPS map). (What ran of this is in section 6: the arms of the fixes at 3x and on Vulkan were cut at the chain's time budget.)

Reading it: `SP\vram19\out\SUMMARY.txt` after `SP\upstream\bench-venv\Scripts\python.exe -I SP\vram19\scripts\summarize.py` (sections: what ran; video memory per run per segment; the scale against 6 GB; what the SDK holds
and which render targets were made when; the fixes off against on; the emulated card; pictures).

## 6. Results

The chain `vram19` ran 2026-10-28 11:38 to 12:16 (one exclusive hold, 35 minutes), RTX 5080 (16 GB), windowed, uncapped, D3D12 unless it says Vulkan, one run per row, the same pad every time
(boot, free roam, 60 s of driving, the pause menu 20 s, the GPS map 12 s). The memory is the game's own "dedicated" figure from Windows' counters (the peak of the 500 ms samples). Frame times from
PresentMon, median and p99 of the segment. Not run: 3x and Vulkan with the fixes (the three steps were cut at the chain's budget), `f_d3_off`.

### 6.6 What the results do not cover

- 3x and Vulkan with the fixes; a race; a real 6 GB card (the reporter's RTX 3060 laptop is not here). The imitation is a 12 GB ballast on a 16 GB card: the OS pages the game's allocations, but over this PC's bus and driver.
- The pressure response (section 4) was not triggered by any run, so its effect on the texture cache limits and the 2 s idle time is not measured; the Vulkan budget query was not run.
- One run per cell: the frame-time differences under 5% are not separated from the spread between equal runs (it was 3 to 5% in other chains of this fork).
- The reporter's numbers (Task Manager, 4.0 GB at 1x and 5.5 GB at 2x, a CPU and a GPU of another class) do not match the game's own 1.7 and 4.0 GB measured here: Task Manager's figure is system-wide, and the difference is not explained.

## 7. Limits

- Written from code and from frame logs of 2 frames each; the key census is an upper bound and does not have the 4x keys of the pause menu.
- The RTX 5080 has 16 GB: it never pages in these runs unless the ballast makes it. Whether the ballast pages the game's allocations and not itself (it is at the highest residency priority) is judged by the emulated runs.
- The reporter's CPU and driver are not here; a CPU-bound 5 FPS (the same slow frames the pause menu showed in issue #17) is a different thing from paging.
- Vulkan: the budget comes from `VK_EXT_memory_budget`; no ballast. Linux and the PS5: not built or run.
