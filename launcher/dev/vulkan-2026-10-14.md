# Vulkan, 2026-10-14

Windows 11, RTX 5080 (Vulkan 1.4, driver API 1.4.351), Ryzen 7 9800X3D, the
fork's build with `--mcla_gpu_backend=vulkan` and the launcher's settings
(`--clear_memory_page_state=false --execute_unclipped_draw_vs_on_cpu=true
--shared_memory_hot_page_faults=4 --shared_memory_hot_page_ms=10000`). Title
screen, its flyover and the attract movie only: a race needs a player.

## Where the time goes at native resolution

The GPU command thread sets the frame rate on Vulkan: it is busy 97 to 99.9% of
the time at native resolution, uncapped (D3D12: 83 to 94%, with the frame rate
held near 144 FPS by both threads waiting on each other). Per draw it costs
about 1.45-1.55 ms of CPU per 1,000 draws against 0.82 ms on D3D12, about 1.8
times as much.

Built-in sampler (`--mcla_profile`) against a RelWithDebInfo SDK, 15 s, a heavy
view (5,200 draws a frame, 8.3 ms frames), GPU command thread:

| Share | Item |
|---|---|
| 30.1% | NVIDIA's Vulkan driver (`nvoglv64.dll`) |
| 7.0% | `VulkanCommandProcessor::UpdateBindings` |
| 2.9% | `VulkanCommandProcessor::IssueDraw` |
| 2.7% | `CommandProcessor::ExecutePacket` |
| 2.5% | `rex::cvar::HasNonDefaultValue` (fixed: `rexglue-vulkan-memexport-check-order.patch`) |
| 1.8% | `UpdateSystemConstantValues` |
| 1.2-1.4% each | texture fetch-constant decoding, sampler parameters, host formats, XXH3, `RequestTextures`, `GraphicsSystem::provider` (called through `GetVulkanDevice`), `WriteRegistersFromMem` |

The main guest thread was 95% busy, 23.5% of it in the GPU-fence spin
`sub_82788F80` (waiting for the GPU command thread).

## Baseline for threaded submission (phase B)

From `vulkan-submission-counters.sdk.patch` (`TMPSUB`), same view:

| Per frame | |
|---|---|
| GPU command thread CPU | 8.25-8.54 ms (98.4-99.9% of the time) |
| Command-buffer recording (pool reset, begin, replay of the deferred command buffer, end) | 1.95-2.01 ms, **about 24% of the thread** |
| `vkQueueSubmit` | 3 submissions, 0.09-0.11 ms (about 1.3%) |
| Blocking fence waits | none |

Recording is the part a submission thread would take over, as
`rexglue-threaded-submission-d3d12.patch` does for D3D12 (where the replay was
23 to 41% of the thread). ForzaHorizon1-ReImagined's 0038 is the precedent for
Vulkan.

## A/B results

In-run switches. "Cycles per draw" is the GPU command thread's cycle count per
swap (`QueryThreadCycleTime`) over draws, each window compared with its
neighbours (`cyc-ab.py`); it shows the thread's own cost even where the frame
rate is held elsewhere. "Frame per draw" is `ab-analyze`-style frame time per
draw. Native, uncapped unless noted; plus or minus one standard error.

| Change | Switch | Cycles per draw | Frame per draw | Kept |
|---|---|---|---|---|
| `gpu_regwrite_bulk` (the common part on Vulkan) | 8 s | | -9.1% +/- 1.0% | yes (already in `rexglue-gpu-regwrite-bulk.patch`) |
| Vulkan port of the block walker | 8 s | -0.5% +/- 0.6% | -0.2% +/- 0.6% | no: `dropped-patches/rexglue-vulkan-regwrite-walker.patch` |
| (D3D12's block walker alone, for comparison) | 30 s | -1.7% +/- 1.0% | | kept as it was |
| Memexport ranges tested before the readback setting | 8 s | **-6.1% +/- 0.6%** | -4.2% +/- 1.5% | yes: `rexglue-vulkan-memexport-check-order.patch` |
| Hot pages on (4 faults, 10 s) against off | 20 s | **-10.5% +/- 1.2%** | -7.8% +/- 2.7% | launcher default already |
| `shared_memory_request_fast_path_with_hot_pages` (hot pages on) | 20 s | -8.9% +/- 0.1% | -7.7% +/- 0.4% | yes (patch) |
| `shared_memory_request_fast_path` | 8 s | -9.2% +/- 0.6% | -5.7% +/- 1.7% | yes (patch) |
| `clear_memory_page_state=false` against `true` | 8 s | **-27.5% +/- 2.6%** | **-46.4% +/- 3.3%** (median frame 7.8 against 11.7 ms) | launcher default already |
| `execute_unclipped_draw_vs_on_cpu=true` at 3x (GPU-bound) | 8 s | -0.4% +/- 0.4% | **-13.9% +/- 1.1%** (71 against 63 FPS) | launcher default already |

Everything the launcher passes and every SDK patch of this fork that applies
to Vulkan helps there at least as much as on D3D12.

A note on method: with 30-second switching the sides lined up with the title
flyover's views (one side always the heavy view), and per-draw costs differ
between views, so runs with 30 s switching were only used where both sides had
similar draw counts. The cycle measure with 8 s switching is the reliable one.

## Vulkan against D3D12

Same launcher settings, fullscreen, uncapped, frames 25-72 s after launch
(the title scene is picked at random per launch, so only runs that drew a
similar number of draws compare):

| | D3D12 | Vulkan |
|---|---|---|
| Native, light view (3,700 draws) | 6.76 ms (148 FPS) | 6.75 ms (148 FPS) |
| Native, heavier view | 6.85 ms at 7,980 draws (146 FPS) | 7.51 ms at 4,970 draws (133 FPS); 8.2-10.4 ms at 5,200-6,800 draws in the A/B runs |
| 3x, the same heavy view (7,850-7,890 draws) | 14.48 ms (69 FPS) | 18.83 ms (53 FPS) |

At native resolution both reach the same ceiling on light views (the main
guest thread and the GPU command thread wait on each other at the game's
per-frame fence); on heavy views Vulkan's GPU command thread runs out first.
At 3x the GPU limits both, and Vulkan's GPU frame is about 30% longer on the
same view: worth a GPU capture (EDRAM ownership transfers and resolves were
two thirds of the D3D12 3x frame).

## Checks

- **Validation** (`--vulkan_validation_enabled=true`, 150 s each: native
  windowed, 3x fullscreen, and native with every setting and cvar of this fork
  off): the same 12 messages in all three, so none from this fork. 10
  `Undefined-Value-ShaderOutputNotConsumed-DynamicRendering` warnings (a pixel
  shader writes a colour output with no attachment bound; the layer stops
  after 10) and 2 errors once, about 16 s in: `VUID-vkCmdEndQuery-None-07007`
  and `-01923` (an occlusion query begun outside a render pass is ended inside
  one). Both are in the SDK's Vulkan backend as released.
- **Attract movie with hot pages** (`rexglue-hot-pages-watched-ranges.patch`,
  which matters most on the PS5): window captures every 60 ms against the movie
  decoded by FFmpeg, as for D3D12. With the fix 10 of 504 captures over 0.3
  from the nearest movie frame, none over 0.4, mean difference 0.181. With the
  fix switched off (a temporary cvar), 82 of 498 over 0.3, 9 over 0.4, mean
  0.227, and the same ghosts of earlier shots over the picture. (D3D12, same
  measure: 15 / 0 / 0.167 with the fix, 116 / 7 / 0.236 without.)
- **Pacing at a 60 cap** (fullscreen, frames 20-100 s): native 98.1% of frames
  within 1 ms of 16.67 ms, worst 18.0 ms (D3D12: 98.4%). At 3x the heavy view
  cannot hold 60 on Vulkan (mean 19.0 ms).
- **Achievement toast** (temporary trigger, 60 cap): 60 presents a second
  before, during and after each toast (a temporary present counter in the
  presenter), 98.1-99.6% of frames within 1 ms while one shows.
- **`--mcla_msaa=false`** at 3x: 13.5 ms against 17.5 ms (-23%, 3,000 against
  5,500 draws), as on D3D12.
- **Mouse pointer auto-hide**: the unattended checks of
  `rexglue-cursor-auto-hide.patch` pass on Vulkan as on D3D12, windowed (17)
  and fullscreen (14).
- **Stress, 15 minutes** (3x, fullscreen, 120 cap): `gpu_regwrite_bulk`,
  `gpu_batch_perf_counters`, `shared_memory_request_fast_path` and `fullscreen`
  switched every 5 s (281 swapchains created), 5 toasts, minimized and restored
  9 times: 60,382 frames, no stalls, no errors, a clean exit.
- **Stress with validation, 5 minutes** (native, the same switching, 2 toasts,
  3 minimizes): no stalls, a clean exit; besides the messages above, 10
  `VUID-vkDestroySwapchainKHR-swapchain-01282` errors (a swapchain destroyed
  while the queue may still use it, on fullscreen switches). A 90 s run with
  only `fullscreen` switching and every setting of this fork off gives the same
  10, so that one is upstream too.

## For phase B and later

- A Vulkan submission thread (ForzaHorizon1-ReImagined's 0038 as the model)
  would take about a quarter of the GPU command thread at native resolution
  (recording), against about 1% for `vkQueueSubmit` alone.
- Forza's 0036 (uploads hoisted out of render passes) was not tried: it is a
  530-line change against a newer SDK, and with hot pages on, uploads are a small
  part of this game's frame.
- `GetVulkanDevice()` reaches the device through `GraphicsSystem::provider()`,
  an out-of-line call (1.2% of the thread); caching the device pointer is a
  small, safe follow-up.
- The 3x GPU frame is about 30% longer than on D3D12 for the same view; a GPU
  capture (RenderDoc or Nsight) would show whether EDRAM transfers or resolves
  cost more on this path.

Not reachable unattended: races, the bike, menus beyond the title, pads.
