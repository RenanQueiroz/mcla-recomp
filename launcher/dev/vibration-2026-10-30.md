# Controller vibration setting (fork issue #31), 2026-10-30

`mcla_vibration` (`src/vibration.cpp`, `config/vibration.toml`), on by default. The game has no vibration setting on any version, so the PC build has one: off, none of the game's rumble reaches a controller, and a motor that is running stops at once. Users: [docs/settings.md](../../docs/settings.md), [docs/off-switches.md](../../docs/off-switches.md), [KNOWN-ISSUES.md](../../KNOWN-ISSUES.md).

## Where the rumble goes (read from the generated code and the SDK source, v0.10.0)

- Guest: `sub_8275CB88(r3 = user, r4 = &{left, right})`, the only caller of `XamInputSetState` in the game. The per-pad update (`sub_82614D30`) calls it when the pad record's dirty byte (+46) is set, so the game asks only when a pad's rumble changes. The function copies the two 16-bit speeds to the stack and calls `bl XamInputSetState` at 0x8275CC34 (r3 = user, r4 = 0, r5 = r1+80).
- SDK: `XamInputSetState_entry` -> `InputSystem::SetState(user, vibration)` -> `SetDeviceVibration` of every device of the user: `SDLInputDriver` (`SDL_RumbleGamepad(..., 0xFFFF ms)`), `XinputInputDriver` (`XInputSetState`), the dev pad's synthetic device (accepts, does nothing). `input_backend` (default `sdl`) names which of the two real drivers exists. `XInputdFFSetRumble` and `XamInputGetUserVibrationLevel` are stubs; nothing else sets a motor.
- No existing option: the string `vibration` in `mcla.exe` is a trigger-mode name in the log of `pc_triggers.cpp`; `mcla_trigger_vibration` is the R2 buzz of the adaptive triggers (another thing).

## Design

A hook in front of the call (`mcla_vibration_set`, above every driver, no SDK patch, so nothing for `patches/README.md`): on, the call goes through; off, it is skipped (the game is told 0, success) unless the drivers were last told to run a motor, in which case it goes through with the motors at 0. The last values the game asked for are kept per user either way. `MclaVibrationFrame` (every game update, on the game loop's thread, from `mcla_frame_delta`) compares what the drivers were last told with what the switch allows (`wanted` if on, 0 if off) and calls `InputSystem::SetState` when they differ: that is the stop when the option is turned off while a motor runs, and the resend when it is turned on while the game wants a rumble. Cost: four atomic loads and a compare per update.

`mcla_adaptive_triggers` (`pc_triggers.cpp`) is not touched. The triggers' report sets only the two trigger enable bits, and SDL's rumble report sets only the motor ones, so neither changes the other (the same as before the switch existed: the game's rumble already went through SDL while the triggers were on).

PS5: the hook is in the shared manifest, so `vibration.cpp` is in the PS5 build's list (`ps5/game/build.sh`) and the pause menu has the VIBRATION row there too; with the option on (the default) nothing changes. Not built or run on the console. The ADAPTIVE TRIGGERS row is PC only (the console's triggers are opt-in, `ps5/game/ps5_triggers.h`). Linux: built with the rest of `src/`, not run.

## The check (chain `vibration`, `C:\mcv\vibration\chain\chain.ps1`)

One shared hold: the branch built with `fast-setup.ps1`, the launcher published as CI does (`publish-launcher.ps1`, into a scratch folder), then one run of `launcher/dev/scripts/vibration.pad` through `devrun.py` (D3D12, native, 60 FPS, a scratch save; `--mcla_vibration=false --mcla_vibration_log=true --mcla_menu_log_layout=true`, the dev pad's synthetic device as the only controller). `mcla_vibration_probe = user,left,right` runs the game's own function (`sub_8275CB88`) on the game loop with those speeds, as if the game had set them, so the real hook and the real SDK call run; the synthetic device logs each call a driver gets. `vibration_check.py` compares the log with what each of the script's steps must show: the option off from the start (the game's rumble: 0 driver calls), turned on with a rumble set meanwhile (1 call from the update), the game's stop and a new rumble with it on (1 call each), turned off while the motors run (1 call from the update: 0,0, none from the game), the game stopping it while off (0 calls), a rumble and its stop while off and then turned on (0 calls); then the pause menu: CONTROLS, the VIBRATION row turned off and on, the ADAPTIVE TRIGGERS row off and on, the log of the options set, the file the menu saved (`mcla.toml.after`), a picture of the page and the page's width (`menu.width`, cap 750; CONTROLS is not the widest page: its widest label is HIDE MOUSE POINTER, wider than ADAPTIVE TRIGGERS by the font table's estimate, 222 against 215 pixels).

**Results** (run 2026-10-30, D3D12, 60 FPS): with the option off the game asked for rumble 4 times and 90 stops, and no rumble reached a driver, only the 1 stop of a motor that was running; with it on, rumble went through, and turning it on again resent what the game had asked for. The menu rows set the option, the CONTROLS page fits (width 581 of 750), and both settings are saved. `vibration_check.py` reports 13 failures, all in steps 9 to 14 and from what it expects, not from the switch: the game sends a stop (0, 0) on every frame while paused, not only when the rumble changes (825 in this run, with the option on), which also clears the probe's values in the pause menu; and one check read a duplicated log line. Those steps' expectations were not changed. **Felt by hand** (owner, 2026-10-30): vibration on and off and adaptive triggers on and off, on an Xbox controller and a DualSense, from the pause menu. The launcher's rows were compiled, not clicked in this test. **Not shown by it:** that SDL's or XInput's driver really stops a motor (the device is synthetic: it proves what reaches the drivers, not what a controller does), the feel on a DualSense or an Xbox controller, Bluetooth, two controllers.

## The owner's check (on a real DualSense and an Xbox controller)

1. Start the scratch build, on a scratch copy of a save (never the install): `robocopy C:\mcv\vibration\dev\pristine C:\mcv\vibration\owner\data /E`, then `& "C:\mcv\vibration\exe\vib\mcla.exe" --user_data_root=C:\mcv\vibration\owner\data --cache_root=C:\mcv\vibration\owner\cache --game_data_root=C:\mcv\base\game --mcla_intro=fast --mcla_vibration_log=true --log_file=C:\mcv\vibration\owner\game.log` (the pad you want to test connected before the start). Drive into a wall at speed, or use the nitro: the pad rumbles. In the log, "vibration: game #n ... to the drivers (on)" lines say the game asked.
2. Pause, Settings, CONTROLS, VIBRATION: A to turn it off. Drive into the wall again: no rumble, and "held back" lines in the log. Hold a rumble (hit the wall and keep the pad in hand), then turn VIBRATION off in the pause menu while it is still going: it stops when you press A, not a moment later.
3. ADAPTIVE TRIGGERS (DualSense only): turn it off, drive: the triggers are slack and the rumble is as VIBRATION says; turn VIBRATION off and ADAPTIVE TRIGGERS on: the triggers push back with no rumble. The launcher's two rows are built (the chain publishes the launcher as CI does) but nobody has clicked them: they are for the first launcher of a release.
