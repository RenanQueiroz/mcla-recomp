### What the frame logs say (`C:\mcv\rain17\fl\p1d-d3d12-x1-gt`, `p2d-d3d12-x2-gt`, two frames each, with the draws, shaders, textures and resolves)

- At 1x the phase `0x02000000` starts with one draw that is the rain: vertex shader `284A04E0`, pixel shader `9A0DCE48`, triangle list, 5,952 indices (992
  quads) in both logged frames, one 128x128 DXT1 texture (`069A4000`), before the frame's depth resolve to `078B0000`. At 2x there is no such draw
  in either frame, and the rest of the frame is the same (the same resolves, the same phases, the draws in the other phases within the traffic's
  variation). The draws of `DB18F472` and `F3FD59A0` that also differ are the volumes of cars' lights (their vertex constants are world positions
  and radii), which follow where the traffic is.
- The frame log is written in `IssueDraw` right after the submission is begun, before the shaders' translation, the pipeline and everything else that
  can leave a draw out; the early returns before it (no vertex shader, a zero surface pitch, no rasterization) depend on the guest's registers, not on
  the scale. So the guest's command stream had no such draw: **the game did not issue it. The SDK did not drop it.**
- The rain's pipeline does reach the SDK at 2x once: `Creating graphics pipeline with VS 284A04E0, PS 9A0DCE48` is in the 2x log at 4.97 s after
  the race mark (3.83 s at 1x), and the texture `069A4000` is created 80 ms later (28 ms at 1x). The first picture is 0.2 s after that, and has no rain.
  Vulkan 2x: the pipeline 6.25 s after the mark, after the first pair of shots, and no rain in the second pair. 3x: the pipeline never (cold
  shader cache, so a pipeline that was needed would have been created). That is: at 2x the rain started a moment later than at 1x and stopped at once;
  at 3x it never started. (Inferred from the pipeline's creation; the shots taken were later.)
- In game time the rain started 553 engine frames (9.2 s) after the race mark at 1x and 716 (11.9 s) at 2x. The runs' frame rates are the same
  (145 FPS at 1x, 144 at 2x D3D12: the game's own sleep), so this is not the GPU keeping up or not.

### Hypotheses of the brief, and what was found

- **(a) The rain's vertex data comes from a resolve or a memexport** into guest memory, stale at scale. Memexport: none. The shader stores of the runs
  (449 shaders at 2x; `C:\mcv\rain17\dev\cache-*\shaders\shareable\*.xsh`, decoded with a small script: the control flow's exec instructions and the
  ALU instructions' export destinations) have no export to `eA` or `eM0..eM4` (destinations 32 to 37). A resolve read as vertex data: the draw is absent, not wrong, and the game's
  command stream is the same at both scales, so what differs is the game's decision. (The frame also resolves small 128x128 `32_32_FLOAT` targets
  (`0561F000` to `0567F000`, drawn with a 4-vertex strip and resolved) that look like a particle simulation's state; they are the same at both scales in the two
  logged frames. That they feed the rain is a guess.)
- **(b) The game reads something back on the CPU.** The SDK's CPU-visible answers that depend on the scale are few: the occlusion queries' sample counts
  (divided by the scale squared), the resolve readbacks (only for resolves that a rule or the readback setting asks for: the vinyl rule `len=1048576,
  pitch=512,height=512,fmt=6;addr=0x051A0000-0x051F7FFF` matches none of the rain frame's resolves) and memexport readback (nothing exports). The
  game reads occlusion queries in one place: `sub_82179720` wraps the Direct3D query read, one caller, `sub_822DD088`, which keeps a ring of two
  queries in a global object (`0x827E1048`) and turns the samples into a ratio of an expected count, for the sun's glare (called from the phase
  `0x02000000`, `sub_823069C0` / `sub_822DD720`). That the rain follows this ratio is a guess; it is the only thing found that takes what the SDK says and
  differs between day and night.
- **(c) The scaled-resolve page classification makes a texture blank.** The draw is absent, not blank.

### The defect found while looking at the query (read in the code, not seen in a run)

`OnPrimaryBufferEnd` (the base SDK; `d3d12_submit_on_primary_buffer_end`, `vulkan_submit_on_primary_buffer_end`, both on) ends the host submission at the
end of every chunk of the primary buffer the GPU command thread executes, and a chunk ends where the game last wrote the ring's write pointer. The safety
net of `EndSubmission` ends an open host query and forgets it. When the end of a chunk falls between the begin and the end of a guest occlusion query, the
guest's end packet finds no host query, `ExecutePacketType3_EVENT_WRITE_ZPD` calls `DisableHostOcclusionQueries()`, and every later query of the run is
answered by the base class with `query_occlusion_fake_sample_count` (1,000 samples). Nothing is logged. How often a kick falls inside the query of a
frame depends on how the game's command buffer fills (the game waits for room more often when the GPU thread is behind; the render markers' "made
room in the command buffer" count was 4 in the 1x run and 16 in the 2x run). This fits what the logs show (a start at 2x, then nothing; at 3x, no
start; the day only; both APIs; none of the fork's scale options), and it is only a fit: the fix is written, the chain tests it.

`patches/rexglue-occlusion-query-keep-open.patch`: while a query is open `OnPrimaryBufferEnd` does not end the submission; a query that is cut anyway
no longer switches host queries off (the last real result of the same buffer, or the fake count, and the next query is a host query again); the log
`occlusion_query_log=N`. Everything is in `patches/README.md` and `KNOWN-ISSUES.md`.

## 2. The pause menu and the GPS map

### What the first chain measured (free roam, D3D12 2x, uncapped, PresentMon, three pause cycles)

Driving 146 FPS with the GPU busy 5.4 to 5.5 ms; the pause menu open 108 to 130 FPS, 7.7 to 9.2 ms (+53%), steady; at native 138 FPS (4.0 to 6.3 ms
busy). One pause of three was slower (73 FPS in the GPU-timestamp run, with more draws: another part of the city). The first chain's `map_zoom`
segment (100 to 140 ms presents) is the title screen's map zoom-out and the loading of the city (the pad's name for the stretch from Start to the
city), not the GPS map; the warm run has up to 27 ms there. The GPS map itself was not timed.

### Where the time goes (the GPU-timestamp frames of the first chain, `gt-phases.py`)

Cycle 2 of `pause-gt-d3d12-x2` (`drive2` and `pause2`, 4 timed frames each; the other cycles: driving 5.7 and 6.2 ms, the pause menu 8.9 and 11.9 ms,
the last one with 1.6 times the draws):

| 2x | Driving | Pause menu |
|---|---|---|
| GPU busy per frame | 4.46 ms | 8.87 ms |
| scene phases (0x800 to 0x04000000) | 1.32 ms | 3.86 ms (2.9 times) |
| pre phases (reflection, environment map, shadow cascades) | 1.90 ms | 2.90 ms |
| draw category | 3.03 ms | 6.19 ms |

In a pause frame the markers show the scene phases 0x800 to 0x04000000 three times, one per tile, and the gaps between tiles (resolves and clears of the
tile) take about 1 ms. The earlier one-tile measurements (`launcher/dev/single-tile-edram-2026-10-16.md`): the scene's GPU time is per-draw cost, and one
tile less is 1.0 to 2.2 ms of GPU and 28 to 35% of the GPU command thread's CPU time. The command thread (recording about 1,370 draws a tile) is
what limits the frame rate in the pause menu: three tiles are about 8 to 9 ms of its time at 2x on a 9800X3D, more on the 5700X3D.

### Why three tiles, and why not one

- The game sizes a tile so that colour and depth take 1,024 EDRAM tiles each (`BeginTiledRendering`, `sub_8217A470`): 4x MSAA 1280x720 is 40x8-pixel
  tiles, 32 per row, so a tile of 1280x256 (32 rows of tiles), three tiles. 2x MSAA is 80x8, 16 per row, 1280x512, two tiles.
- One tile of 4x MSAA 720p is 32 x 92 = 2,944 EDRAM tiles a surface, 5,888 with the depth. `OneTileFits` in `src/render_perf.cpp` needs a surface of at
  most 2,048 tiles (as far as a host render target reaches from its base, the SDK's choice: "as tall as the console's EDRAM from their base, so they take
  no more memory") and both within `edram_tiles` (4,096). 2,944 is over both.
- A larger EDRAM would need 8,192 emulated tiles: 12-bit render target bases, 22 resolve shaders per API that exist as compiled copies per size (the
  4,096-tile ones were built with fxc and glslang), transfer shaders that pack base differences, an EDRAM buffer of 160 MiB at 2x and 360 MiB at 3x. Not a
  setting; not done.
- **What fits is two tiles**: 64 rows of tiles = 1280x512 is exactly 2,048 tiles a surface, 4,096 for both. It is the tile the game itself uses at 2x
  MSAA. `mcla_larger_tiles` (`src/render_perf.cpp`): the hook makes the tile twice as tall and the count 2 for a pass the game would draw in more than two
  tiles and that cannot be one tile. The game's loop does the rest (rectangles, bins, resolves). A third fewer draws a frame in the pause menu, the race
  pause and the GPS map. Expected, from the numbers above and the one-tile measurements: about 1 ms of GPU and 2 ms of the command thread's time in a
  pause frame. **Not measured.**

### Not done

- 2x MSAA behind the pause menu (one tile, the SDK has it): a different picture.
- Leaving out the static off-screen phases (shadow cascades, reflections, environment map: 2 to 3 ms of a paused frame) while the world stands still:
  the same picture in the pause menu, but the GPS map is a different scene each frame, and nothing found tells a paused world from a map reliably.
- Making each draw cheaper on the command thread, or culling a tile's draws that lie outside it (the guest does not say where a draw lands; the SDK would
  need the vertex shaders run on the CPU).
