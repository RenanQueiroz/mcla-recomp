# HDR output (2026-10-16)

How the fork's HDR output works, how each part was checked, and what is left.
Windows, RTX 5080, D3D12 and Vulkan, `devrun.py` runs on a copy of the save
data (real save data, achievements, shader cache and `mcla.toml` hashed before
and after every session: unchanged). The display: Windows HDR on, DXGI peak
1317 nits (HDR Calibration profile), SDR content brightness 240 nits.

The patches, in the order they apply (FORK.md):

| Patch / file | What |
|---|---|
| `src/render_markers.cpp` (game) | PM4 NOP markers in the command stream: frame start/end, the end of the 3D scene, the tone map, the UI, the end of the render loop |
| `rexglue-guest-markers.patch` | the SDK reads them: `CommandProcessor::OnGuestMarker` |
| `rexglue-hdr-output.patch` | HDR10 swap chains, the display's levels, the refresher writing PQ, the presenter's own UI as a layer, captures back to SDR, settings |
| `rexglue-hdr-ui-layer.patch` | the game's HUD and menus as a separate premultiplied layer; the review fixes of phases 0-2 |
| `rexglue-hdr-scene-mcla.patch` | the game's scene in HDR, from its tone map's inputs (this game only) |
| `src/settings_menu.cpp`, `launcher/src/` | the DISPLAY rows; the launcher's HDR drop-downs, level sliders and tips |

Settings (all change during play): `hdr` = `off` / `auto` (when Windows has
HDR on for the display; the game's default on Windows since the look was
signed off, set in `MclaApp::ApplyPcDefaults`; the SDK's own default stays
`off`, and Linux and the PS5 keep it) / `on`; `hdr_peak_nits`,
`hdr_paper_white_nits` (0 = what the display reports; the menus step them
from 200 to 4,000 nits by 50 and from 80 to 480 by 10), `hdr_ui_nits` (0 =
paper white), `hdr_sdr_eotf` (`srgb` or `gamma22`), `mcla_hdr_highlights`
(1, 1.5, 2, 3; 2 by default), `mcla_hdr_bloom_gain`, `mcla_hdr_knee`; for testing,
`hdr_test_pattern` and `hdr_debug_ui`; to turn parts off, `hdr_ui_layer`,
`mcla_hdr_scene`, `mcla_render_markers`.

## The pieces

**Markers (game).** `sub_822C0980` (the frame), `sub_822E6408` (the render
phase loop) and `sub_822E55D0` (a phase's start, with the phase bit) are
overridden; at their boundaries a 3-word NOP packet (`'REXM'`, kind, value) is
written into Direct3D's command buffer, only on the render thread. Past the
buffer's limit the marker makes room with the game's own routine
(`sub_82412710`), which every Direct3D packet writer calls before writing a
word: these call sites are renderer functions never called from inside
Direct3D, whose callers don't hold the write pointer, so the game's next
Direct3D call would make the same call in the same state. In a 90 s run room
was needed once (before the review it was skipped, losing that marker).
Screenshots with the markers on and off: identical at every still pixel at 3x
on both APIs.

**Output (presenter).** While `hdr` asks for it and the display is in HDR mode
(DXGI's colour space; `on` also tries without), the swap chain is HDR10:
D3D12 `R10G10B10A2` with `G2084_NONE_P2020` (`CheckColorSpaceSupport`,
`SetColorSpace1`, `ResizeBuffers` on a switch), Vulkan `A2B10G10R10` with
`HDR10_ST2084` (`VK_EXT_swapchain_colorspace`). The swap's refresher
(`hdr_refresh.cs`, in place of the gamma pass) writes PQ BT.2020 code values
into the guest output, after putting SDR values through the guest's own
256-entry display table, so DISPLAY GAMMA (`tv` / `pc`) means the same in HDR
and switches during play. The presenter then only scales (bilinear; FSR, CAS
and dithering are skipped in HDR), draws its own UI (ImGui, toasts) into an
8-bit layer and composites it over the PQ image at the SDR level, and sets
HDR10 metadata (BT.2020, D65, the peak as MaxCLL and mastering maximum).
Captures (the dev pad's `shot`) turn HDR10 back into SDR relative to the SDR
white level: SDR content comes back within 1 level (99.92% exact); light above
SDR white is clipped keeping its hue, and the roll-off is not undone, so
captures can't show highlights (`hdr_debug_ui 8` is for that).
The display's levels are read on a thread of the presenter's own, about once
a second while `hdr` isn't off and on SDL's display and HDR events (DXGI
`GetDesc1` 2-4 us, `QueryDisplayConfig` with the SDR white level 25-80 us,
the first DXGI factory 0.5 ms); the first connection waits for the first
reading, so it starts in HDR10 rather than switching. A change of the
display's HDR state reconnects. A guest output that can't be PQ (no
refresher, a PWL gamma ramp) keeps the swap chain SDR.

**UI layer.** From the UI marker, the render target the UI phase draws to
(1x `8_8_8_8` in play, the tiled 4x `8_8_8_8` pass in the menus) is copied
(the underlay) and cleared to 0 before its first blended draw, per tile;
blended draws (`SrcAlpha` or `One` / `InvSrcAlpha`) get the alpha blend
`One` / `InvSrcAlpha`, so the target collects the UI premultiplied with its
coverage in alpha. When the game resolves that target to the front buffer
(found from the resolve's own destination: its base's tiled position in the
front buffer plus its offset), the UI and the underlay are copied to
screen-space textures and the target is put back (UI + underlay x (1 - alpha),
colour and alpha, one blended draw) before the game's resolve, so the game's
8-bit frame is what it was. Another blend, another format, or the target
resolved somewhere else mid-UI end the separation for the frame (the target
is put back at once): the frame then falls back to the difference between
the front buffer and the underlay, or, if the target never reaches the front
buffer, to the whole frame as SDR. A frame with the tone map but no UI pass
is all scene; one without the tone map (legal screens, logos) is all SDR.
On Vulkan the render target copies are a compute shader through the target's
sampled view (4x averaged in the shader), so render targets need no extra
usage.

**HDR scene (this game only).** The colour draws between the tone map and
UI markers are looked through for the tone map's shaders (VS
`1FAB9787BCA32D7C`, PS `E5EBEFAE4D165CBA`); that draw must also go to a 1x
`8_8_8_8` target, cover the whole output and have the fetch constants the
pass expects (second review, below). Right after it, `hdr_scene_mcla.cs` runs the game's
operator again from the same textures (pixel shader fetches 0-2: the scene,
motion blur, bloom; vertex shader fetch 16: the adapted luminance; bound as
2D arrays as the texture caches bind them) and constants (PS c64.z key,
c65.x white squared, c67.x saturation, c68.xyz balance, c69.x contrast,
c252.w blur weight, c255.w epsilon; VS c64.x / c65.x luminance clamp),
sampling where the game's draw samples (its half-pixel offset at the
resolution scale: one host pixel at 2x and 3x; point-sampled scene, bilinear
blur and bloom). It writes the scene in the game's linear units (1 = its
white) to an FP16 texture: Reinhard extended as the game computes it up to
the knee (`mcla_hdr_knee`, 0.6), then an exponential shoulder with the same
value there that approaches the peak in the game's units (the viewing
transfer inverted on the CPU through the display table), its slope the game
curve's times `mcla_hdr_highlights` but at least what reaches the game's
white at its white, and never under the game's curve below its white (second
review); then bloom (`mcla_hdr_bloom_gain`), saturation, colour
balance and contrast as the game does. The draw's own output is copied too.
In the refresher, wherever the 8-bit picture under the UI is that output, or
brighter by light added after it (the night glows, coronas and beams), the
scene comes from the FP16 texture plus the added light (their 8-bit
difference, decoded, times the highlights setting); where something darker
was drawn over it, the 8-bit picture stays (`hdr_debug_ui 1` shows those
pixels in cyan: under 0.1% in every scene below). The UI is blended over the
scene in the game's code values, as the game blends it, before the display
table (extended above 1 along its last step) and the SDR decode (extended
too); paper white is where the game's white lands, `hdr_ui_nits` moves the
UI's share to its own level, and everything above 0.75 of the peak rolls off
towards it.

## Checks

**Scene list (UI layer), both APIs, after the review fixes.** Every scene got
the UI layer, with no fallback: legal screens and the Rockstar logo (no tone
map: the whole frame as SDR, as intended), the Bink intro and attract movie,
the title screen, the map zoom-out, the gameplay HUD, the pause menu and its
fades, the GPS map and its fade, the race menus, loading, race intro,
countdown, start, the race, race pause, replay confirmation, replay, the
race-over screen with its NEXT RACE dialog and the next race's intro. Not
reached: the garage, photo mode, cutscenes. Two single frames at race
transitions had the tone map but no UI pass; they are composited as all scene
since phase 3.

**Restore error** (the target put back, against the game's frame without the
layer, over still pixels, 3x; D3D12 and Vulkan alike): pause 94.5% exact,
99.99% within 2 levels; GPS 85.1% exact, 99.94% within 2; roam 97.2% exact.
The larger differences are on animated menu elements (rotating ring, pulsing
CONTINUE, GPS icons).

**The game's curve through the scene pass** (`hdr_debug_ui 7`, against the
game's own frame, pause menu, 3x): 86.5% identical, 95.5% within 1 level,
97.3% within 2, on both APIs. The rest: columns where the GPU's sample lands
on the neighbouring texel (a third of a game pixel at 3x) in fine detail, and
per-channel clipping in the brightest areas. Below level 190, the HDR
output's SDR capture matches the game's frame within 1 level on 95% of pixels
(the display table is interpolated between codes in HDR).

**Levels** (`hdr_debug_ui 8` captures; paper white 240, peak 1317,
highlights 1): day 424 nits at most (0.08% of pixels above paper white), dusk
814 (1.8%, sky and a lit billboard), night city 456 (0.01%), night race 1167
(0.09%: headlights, tail lights, glows). The highlights steps 1, 1.5, 2, 3 at
dusk: 785, 975, 1086, 1209 nits at most; the median stays at 6.5 nits.

**GPU time at 3x** (GPU timestamps, all HDR work per frame, median): D3D12
0.48 ms (scene pass 0.18, copies 0.11, refresher 0.12, restore 0.03),
Vulkan 0.56 ms (scene pass 0.17, copies 0.19, refresher 0.13, restore 0.03),
against 0.04 / 0.03 ms for the SDR gamma pass. Phase 1's refresher alone:
60 us against 35 us.

**Pipelines.** The alpha-overridden UI pipelines (about seven) are new
pipelines; with an empty cache, turning HDR on in the city left no draw out
on either API (they were ready within the frame's wait budget).

**Validation.** D3D12 debug layer (bindless and bindful): nothing from these
changes. Vulkan synchronization validation through HDR on, off and on: only
what it reports without them (`vkCmdEndQuery` 07007/01923, write-after-write
hazards between compute dispatches). The swapchain recreation on an HDR
switch used to report `VUID-vkDestroySwapchainKHR-swapchain-01282` (the
presenter destroyed the old swapchain without waiting for its last present,
an upstream bug that any recreation hit); it now waits for the present
queue.

**HDR off.** The swap chain, the refresher, the presenter's paint and
captures are today's; the UI layer and the scene pass don't run (they need
HDR output active); markers are still written and read. Boot frames are
byte-identical to the build before the UI layer on both APIs (3D scenes
can't be compared between runs: the game isn't frame-deterministic, the pause
camera differs between runs of one build). What HDR off still costs: the
markers; a check per draw; the refresher's and the scene pass's pipelines,
the presenter's two HDR pipelines and a few descriptor sets created at
start-up; and the pipeline storage keeps the alpha-overridden pipelines from
earlier HDR sessions and creates them at start-up.

  cyan; 2 the game's own frame; 3 to 6 the UI layer's colour and alpha, the

## Second review (phases 3-4)

An independent review of phases 3 and 4 found no crash-class bug; these were
fixed (the scene patch, `src/render_markers.cpp`, `src/settings_menu.cpp`):

- **The shoulder at Normal was darker than the game's curve between the knee
  and the game's white.** By day and at dusk the game's white squared W is
  small (0.335, 0.214): above the knee its Reinhard curve bends up towards its
  white, while the shoulder, leaving the knee with the same slope, bends down,
  so it stayed under it all the way to white (at the game's white 4.9% darker
  by day and 5.4% at dusk with peak 1317 and paper white 280, 7 to 7.5% at
  600/240, 11 to 12% at 400/300, 16% with the peak at paper white;
  `hdr/shoulder_fix.py`). Now the shoulder's slope is at least what reaches the
  game's white at its white (s' = -span ln(1 - (1 - K) / span) / (sqrt(W) -
  Ls_K)), the shader takes the game's curve where that is higher below its
  white (a concave shoulder over a convex curve with the same ends never dips
  under it; the max is for W > 1, where both bend down), and with the peak at
  or below the game's white there is no shoulder: the game's curve, clipped at
  its white. Brighter, the default and the look the user signed off, already
  rose faster than that and is unchanged. Measured in the same paused frames
  with the old shoulder behind a temporary switch (`hdr/make_levels_ab_pad.py`,
  `hdr/levels_ab.py`; D3D12, native, `hdr_debug_ui 8` captures, the brightest
  channel's maximum and 99.9th percentile in nits):

  | Frame | Peak / paper white | Normal before | Normal after | Brighter before and after |
  |---|---|---|---|---|
  | Day | 1317 / 280 | 875, 366 | 975, 380 | 1125, 456 |
  | Dusk | 1317 / 280 | 1086, 705 | 1125, 757 | 1209, 1010 |
  | Night | 1317 / 280 | 456, 181 | 456, 181 | 731, 188 |
  | Day | 600 / 240 | 509, 305 | 527, 328 | 527, 380 |
  | Dusk | 600 / 240 | 547, 490 | 567, 509 | 567, 527 |
  | Night | 600 / 240 | 340, 155 | 366, 155 | 509, 161 |

  At Brighter, 0.03% of the pixels differ between old and new in every frame:
  as many as where the curve is the same (night at Normal, peak 1317), the
  pause screen's own animation. Near the game's white (8-bit levels 0.8 to 1.0
  of it, right of the pause menu) the HDR/SDR ratio's 5th percentile at Normal
  went from 0.96 to 1.00 at night with 600/240 (by day it stays at 0.96 both
  ways: one PQ step of the 8-bit capture, the pass's own one-level
  differences from the game's frame).
- **The shoulder's top and the presenter's roll-off stack.** The shoulder maps
  its limit to the peak, and the presenter rolls off from 0.75 of the peak, so
  the scene's brightest highlights reach about 90% of the peak setting; bloom
  and contrast take some past that. Left as it is (the look was signed off);
  the docs and the launcher's tip say so.
- **"(NOT AVAILABLE)" was decided once per session**, and never with the game
  started with `hdr` off (the display is only read while it isn't). Opening
  DISPLAY now reads the display (`Presenter::RefreshHdrDisplayInfo`, which
  wakes the display thread and waits up to 250 ms for a query that started
  after the call; well under a millisecond here), and the label is
  recomputed whenever the list is drawn. Checked with `hdr = off`: opening
  DISPLAY logged the display's state.
- **The tone map draw was recognised by its shaders and target only, and
  only as the phase's first draw.** Now every colour draw of the tone map
  phase (to the UI marker) is looked at; the one with the tone map's shaders
  must also cover the whole output (the scissor at 0,0 at least the output's
  size, no window offset, the viewport within a pixel of it: the game's is
  640/640 by -360/360 at 1280x720) and have the fetch constants as the game
  sets them (logged once to write the check: fetches 0 to 2
  `k_16_16_16_16_EXPAND` with signed components, the identity swizzle,
  clamp to edge, point (0) and bilinear (1, 2); the vertex shader's 16
  `k_32_FLOAT` 1x1, swizzle X111, point; no exponent bias; the scene at the
  output's guest size). A frame where it isn't keeps the 8-bit scene, and
  every change of the outcome is logged with the hashes and the reason. A
  first version expected unsigned float formats and fell back, as it should,
  with the reason logged.
- **The glows' gain applied to anything drawn after the tone map.** It now
  applies only while every draw on the tone map's target between it and the UI
  adds light (dest factor One, Add); the night glows are `One` / `One`
  (RB_BLENDCONTROL 01010101, pixel shader F7E0610D4F088236), so they keep
  their look; any other draw there makes that frame's difference count at gain
  1, logged when it changes.
- **The markers' make-room call could leave the host's MXCSR out of step**
  with the context's cached FPSCR (sub_82412ED0, under sub_82412710, turns
  flush-to-zero off; `ctx = saved` put back the cache but not the register,
  and `enableFlushMode` skips the write when the cache matches): MXCSR is put
  back to the caller's rounding and flush modes (`restoreGuestBits`, as the
  SDK's own context restore does).
- **Weaker hardware:** the HDR textures (about 200 MB at 3x) are released 120
  swaps after HDR output goes off (deferred until the GPU is done), and made
  again when it comes back (checked on both APIs, under the D3D12 debug layer
  and Vulkan synchronization validation); the scene pass no longer runs where
  its copies can't (no host render targets) or in the debug views that don't
  show the scene.
- **Smaller ones:** the adapted luminance is read at its texture's middle texel
  (3x3 at 3x); a frame's HDR scene is only used at the output size it was made
  at (frames without a UI pass had no such check); NaN can't reach the output
  (Ls clamped to 0..1e18 and NaN-checked by its bits, the pass's output and
  the refresher's table index too: a compiler may fold x == x); the display
  thread's destructor only tries its lock (for 100 ms) and leaves the thread
  alone if it can't have it, since at exit on Windows it runs after the
  thread was ended, possibly holding it.

Also in this round: PEAK BRIGHTNESS and PAPER WHITE in the pause menu step by
50 and 10 nits (AUTO first, the ends don't wrap), a value set by hand between
the steps shows as it is (537 NITS) and steps to the next step that way (550);
the peak never goes below paper white (a step that would cross it stops at
the last one that doesn't; the other isn't moved). The game repeats a held
left or right after about 7 frames and then every 6 (40 ms apart at 150 FPS,
200 ms at 30; the key code is the same, '3' or '4', for a press and its
repeats), so the menu reads user 0's pad every frame while a submenu is
open (`MclaTickSettingsMenu`) to tell a hold from new presses: a press steps
once, a hold steps again after 0.4 s, at most every 0.1 s, then on every
repeat from 1.2 s and four times as far from 2.2 s, with repeats further
apart than 50 ms stepping more each, so the speed is about the same at any
frame rate (a 100 ms tap: 1 step; a fast double tap: 2). The launcher has
sliders with an *Auto* box for them, and an "i" tip on every setting.

**GPU time at 3x after the fixes** (the same timestamps, 41 to 46 frames, all
HDR work per frame, median): D3D12 0.51 ms (scene pass 0.20, copies 0.15,
refresher 0.13, restore 0.03), Vulkan 0.51 ms (0.20, 0.15, 0.13, 0.03), the
SDR gamma pass 0.04 / 0.03 ms. The scene pass takes 0.02 to 0.03 ms more than
before (the NaN checks, the max with the game's curve).

**Checks after the fixes:** the scene list on both APIs at 3x, every scene on
the UI layer with no fallback and the tone map found throughout; the D3D12
debug layer through HDR on, off (textures released) and on: only its
existing warnings (buffers' initial state, MIN/MAX blend states); Vulkan
synchronization validation the same as before (`ShaderOutputNotConsumed`,
write-after-write between compute dispatches on a buffer, `vkCmdEndQuery`
07007/01923), also through the textures' release; `--hdr_test_pattern=true`
on the command line (as the launcher's *More mcla.exe options* passes it)
shows the bars; with `hdr` off (normal intro, 3x), every steady boot frame
byte-identical to the phase 1 build's on both APIs (24 and 28 of 35 shots
had an identical one; the rest are the legal screens' fades and the logo
animation caught at another moment: the text's brightness 32.6 against 37.5
in the same fade).

## Not done or not verified

- Only Windows with NVIDIA. The PS5 build applies the patches but hasn't been
  compiled with them; HDR stays off there (no DISPLAY rows). Linux (HDR10 on
  Wayland) comes later: the presenter would use HDR10 where the surface offers
  it, but the display's levels are read only on Windows.
- scRGB (FP16) output: HDR10 only for now.
- The garage, photo mode (freeze frames would show as SDR) and cutscenes were
  not reached.
- The look was signed off by the user on an ASUS ROG Swift PG32UCDP (WOLED, Gaming HDR mode, Uniform Brightness on), 2026-10-16
  (Auto peak and paper white, Highlights at Brighter), and `hdr` became `auto`
  by default on Windows. Other displays, and switching Windows HDR while the
  game runs, are not verified.
