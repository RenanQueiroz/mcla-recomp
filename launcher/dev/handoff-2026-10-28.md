# The hand-off trace (2026-10-28)

What it is and how to read it: `patches/README.md`, `rexglue-handoff-trace.patch`; the options and the script in
`launcher/README.md` (Measurement tools, "The hand-off trace"). This note holds what was measured with it.

## State when this was written

Nothing has been run. The patch, the hooks (`config/handoff_trace.toml`), `launcher/dev/handoff_trace.py` and the two pads
were written and checked as far as no game allows: the SDK builds in CI with the patch applied, the host sources compile
against it (stand-ins for the generated headers), `check_pins.py` passes, and the script reads a synthetic trace in the file
format (written independently of the C++ writer from the layout in the script's header). The hooks' addresses come from
the generated code (`sub_82148A10` entry, loop head `0x82148AA8`, exit `0x82148AE8`; `0x82161880` after the last store of
`sub_82161210`; `sub_82144888` entry; `0x82160144` after the store in `sub_82160088`; `0x82305E90` in `sub_82305E38`;
the entries of `sub_822C0980`, `sub_82305D00`, `sub_823057E8`, `sub_82131008`) and have not been through codegen yet.

## What the profile led to expect (from `profiling-2026-10-26.md`, before the pump wake on demand)

Free roam, 16 logical processors, D3D12, native, uncapped: 6.82 ms a frame; the update thread 6.46 ms of CPU, 2.8 of it in the
ring-slot wait; the render thread 3.83 ms; the render thread waiting for work 35% of the time while the update thread ran,
the update thread polling 27% while the render thread ran, both running 25%. With the pump wake on demand (v0.2.0) the frame
is 4.17 ms at 16 logical processors: about the render thread's CPU, so little is left to win there. At 4 logical processors the
default is the game's own 7 ms Sleep (the wake on demand failed the audio check there) and the CPU, not the hand-off, is
the limit.

## The early wake of the frame-pacing thread (`mcla_pump_wake_early`, branch cpu/handoff-prewake)

The one candidate the code suggested before any trace (so it is a hypothesis, not a result). With `mcla_pump_wake_on_demand` the round
of the frame-pacing thread that frees the ring slot (`sub_82144888`, which calls `sub_82160088`; the slot is freed early in the round, before the 24 per-frame callbacks and the XAM call: the order of the calls in the generated
code, not measured) starts when the main thread asks for the slot: the main thread is
in the ring wait (`sub_82148A10`) for the thread's wake-up and the start of its round. The slot becomes needed the moment the main
thread publishes the previous one (the last statement of `sub_82161210`, a store of the ring's head word: nothing before it can make the
slot free, since the thread frees `(head + 2) mod 3`), so a round started there runs beside the rest of the main thread's frame, and
the slot is free when it asks. Why it is believed safe: the thread's rounds already run at any moment in the main thread's frame at its
7 ms rhythm (the wake on demand only picks the moment); this one picks a moment inside the window in which a round is useful at all, once
per frame, and only while the thread's last wait was ended early (the regime in which the frame is shorter than the thread's rhythm, so
under a frame-rate cap, or a slow frame, nothing changes). What it does not change: the rounds' count (one a frame), the guest's data.
What it can change: the time of the audio listener's extrapolation (from the generated code: a round samples the clock and extrapolates from the ring's newest entry; not verified), by up to
a frame, towards the publication of the sample.

The A/B in the chain (`hab`): `wake-ab.pad`, 16 logical processors, both variants with `--mcla_pump_wake_on_demand=true`, `off` with
`--mcla_pump_wake_early=false`, `on` with it true, 1 warm-up and 3 runs a side, real-time steps, audio statistics; the report is
`wake_report.py`'s (rule: frame at most 1% and p99 at most 3% longer on every segment; the gain asked of the wake on demand, 3%, is
more than this can give if the ring wait is a few percent of the frame, so read the frame medians).

Gain expected: at most the ring wait's share of the frame if the main thread is on the critical path, and nothing if the render thread is.
The trace says which (the "Critical path" and "Hand-off numbers" sections of a city window at 16 logical processors).
