# mcla.exe that stays alive after the game is quit (2026-10-29)

What was seen, what is known of the cause, what the tool measures, and how to run it. Nothing in this note was measured with the fix yet: the chain below is the first run.
User-facing text: `KNOWN-ISSUES.md` ("mcla.exe stayed alive after the game was quit"); the switches: `docs/off-switches.md`; the patch: `patches/README.md`
(`rexglue-exit-gpu-drain.patch`).

## What was seen

After a scripted run quits, the log has `Window closing, shutting down...`, `Execution complete` and `Title terminated; hard-exiting process.` (in either order of the last
two), and the process does not end.

| Where | What |
|---|---|
| `stressdef` run `sds-S-r4` (v0.3.0, 2026-10-29) | alive 330 s after the line, until the test driver closed it; one thread, "D3D Background Thread 0", 0 CPU in `GetThreadTimes` |
| `stressdef2` chain (v0.3.1 build c1ff3f3, affinity mask 0x55 = 4 logical processors, 4 busy processes in the same job object) | 11 of 14 usable runs and warm-ups still alive 20 s after the line (the chain's watcher then tried to end them); the same in the variant that has none of the small-CPU options |
| the 980 earlier runs in all result files under the scratchpad | 1 (S-r4) |
| the fork owner's own unstarved runs | "about 1 in 10", not in a result file |

Read from the thread logs (`threads.csv`, `mem.csv`) of those runs:
- Within a second of the line the process has exactly **one** thread, "D3D Background Thread 0". In a run that ends normally the last sample before the end has 83 threads, with
  "D3D Background Thread 0" to "3" among them. The name is set by neither the SDK nor this fork; it comes from the Direct3D 12 runtime or the GPU driver.
- Working set (1.6 GB) and private bytes (2.1 GB) do not change for as long as the process lives, so the address space is not torn down.
- That thread's cycle count rises by a steady 3.0 million a second (0.1% of a core) while its `GetThreadTimes` CPU time does not move: it wakes up about 1,000 times a second.
  It is not blocked forever and not busy.
- The driver reported `exit 0` after 200 s (the 170 s timeout plus 30 s) for every one of them: the process's exit code is 0, the game's own `std::_Exit(0)`. An outside
  `TerminateProcess(handle, 1)` 20 s after the line (the watcher) and the driver's own kill did not change it. So the kernel had taken the exit (the process was terminating),
  every thread but one had gone, and that one did not leave. (Inferred from the exit code; the tool below reads `IsProcessDeleting` and `ThreadIsTerminated` to check.)

## The shutdown path (read from the sources)

`ReXApp::OnClosing` (SDK `src/ui/rex_app.cpp`, compiled into `mcla.exe`): `TerminateTitle()` (it stops the game's own threads and waits at most 200 ms; stragglers are left
running), the two log lines, `FlushLogging()`, `std::_Exit(0)`. With llvm-mingw on the UCRT that is `_exit`, which calls `ExitProcess`: Windows ends every other thread, then runs
`DLL_PROCESS_DETACH` of each DLL on the calling thread, then ends the process. Every way of quitting reaches it: the pause menu's QUIT GAME (`CloseGame` in
`src/settings_menu.cpp`), the close button (`MclaApp::OnWindowCloseRequested`), the dev pad's `quit` and `close`. Nothing stops the GPU first: the command processor, the
submission thread, the pipeline threads and the storage writer run until `ExitProcess` ends them, in the middle of calls into the driver, with work on the GPU's queue.

**Inferred, not measured:** the lone thread is inside a driver call that does not end while the GPU has not finished what it was given, and the busy processes make that
likely by slowing the threads that would otherwise have finished it. This is a hypothesis; the tool is built to test it.

## The patch (off)

`exit_gpu_drain_ms=N` stops the GPU command processor (bounded by N ms) before the hard exit; `exit_terminate_process=true` ends with `TerminateProcess`. Details:
`patches/README.md`. Neither is on by default. They are on only after a measured run set in which every exit is within 2 s.

## The tool: `launcher/dev/exit_probe.py`

Runs short boot-to-free-roam-and-quit runs (`scripts/exit-pause.pad`: QUIT GAME in the pause menu; `exit-close.pad`: WM_CLOSE; `exit-end.pad`: the script ends) on scratch
copies of the save, as `devrun.py` does, and for each run measures:
- `line_to_exit_s`: from `Title terminated; hard-exiting process.` to the end of the process (the process handle is polled every 20 ms; the line's own time stamp is the start);
  `close_to_line_s`: from `Window closing` to that line (`TerminateTitle`, and with the fix the GPU stop); `gpu_stop`: what the log says about the stop.
- A process still alive 3 s after the line is looked at: the kernel's view of the process (`IsProcessDeleting`, exit status) and of each thread (state, wait reason, wake-ups a
  second from two samples 2 s apart, `ThreadIsTerminated`, the last system call), the GPU engine use of the pid, a stack scan of the thread (RIP and RSP when it can be
  suspended; the values on its stack that point into a module, with the nearest export name), and a minidump (`dump.dmp`, stacks and thread info, no heap). Then it is nudged, one
  thing at a time, 4, 9, 14 and 19 s later (TerminateProcess, WM_CLOSE, TerminateJobObject, `Popen.kill`), each logged with its time and result, so that what ends it, if
  anything, is recorded. After 45 s the run is given up on; the batch waits 60 s more and stops if the process is still there.
- Cells: **U** all threads, D3D12; **V** all threads, Vulkan; **A** affinity 0x55; **S** 0x55 and 4 busy processes (the stress that hung 11 of 14). Modes: **0** as shipped;
  **T** `exit_terminate_process`; **D** `exit_gpu_drain_ms=1500`; **DT** both. Cap 120, 1x, windowed, intro fast, `--vsync=false`, the shader storage seeded from the stressdef2 chain's.

`python -I exit_probe.py selftest` runs the system queries, the stack scan and a dump on a stand-in process, and the report on made-up rows (no game). It passed on 2026-10-29
(the thread state, `ThreadIsTerminated`, RIP/RSP and the nearest export names work; `ThreadLastSystemCall` answered "access denied" on the stand-in, so the last system
call may be missing in the report).

## Running it (hold 1 and hold 2) and reading it

See the head of `C:\mcv\exithang\chain\chain.ps1` for the queue commands. Hold 1 builds the branch (the SDK has a new patch: about 3 minutes) and runs 18 runs (about 28
minutes in all). `SUMMARY.txt` lines start with `EXITHANG`: `FREQUENCY` (runs that took more than 2 s or never ended, by cell, as shipped), one line a cell and mode with the
median and the longest exit, `HANG` blocks (what the process was, per hang), `MODE` (does the mode exit within 2 s in every run), `BEST MODE`, and `DEFAULT` (whether the numbers
allow turning a mode on by default: every fix-mode run within 2 s, at least 4 in cell S and 8 unstarved). Hold 2 repeats the best mode of hold 1 where hangs are common and
where they are rare.
