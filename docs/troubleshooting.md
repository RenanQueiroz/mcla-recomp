# Troubleshooting

The short version is in the [README](../README.md#if-something-goes-wrong). Setup, build and run problems, each with what to do.

## If something goes wrong

| If | Then |
|---|---|
| The setup wizard's first page says *Couldn't find the latest release* (*GitHub didn't answer in time*, *Couldn't connect to ...*, *The DNS lookup for ... failed*), or the launcher says it *couldn't check for updates* | The message says where it stopped: the DNS lookup, connecting to `github.com`, connecting to the download host GitHub sent the file to (`release-assets.githubusercontent.com`), the secure handshake, no answer, or reading the file. **Copy details** (the page; the launcher's bar has it too) copies what was tried: the addresses of each host with IPv4 or IPv6 and how long each took, the redirects, the proxy in use and the errors; paste it into an issue. The program already tries IPv4 and IPv6 together (a network that advertises IPv6 but does not route it used to stall it), tries once more and then asks GitHub's API, so what is left is between the PC and GitHub. Try, in this order: open `https://github.com/RenanQueiroz/mcla-recomp/releases/latest/download/release.json` in a browser (the page has a button; a small file downloads when GitHub is reachable); turn a VPN off or on; check the system proxy (*Settings > Network > Proxy*) and what the antivirus or firewall does to `github.com` and `githubusercontent.com`; check the PC's date and time (*the secure connection could not be set up*). *Its limit of requests for this address is used up* is GitHub's API (60 an hour without signing in, per internet address, shared by everyone behind the same one): wait for the time shown. If a browser downloads the files but the setup cannot, use the wizard's **Use files I downloaded** (below the error): download `release.json` and the SDK zip (`rexglue-sdk-...-llvm-mingw-....zip`, not the one with `source` in its name) from the [releases page](https://github.com/RenanQueiroz/mcla-recomp/releases/latest) into one folder, choose it, and the page lists the four build tools to download there too, each with its link; every file is still checked against the release's checksums. (The setup then still gets the source with `git` from `github.com`.) |
| Updating to v0.3.1 fails at step 5/6 with `has been modified since the precompiled header` | Fixed in v0.3.2: press **Update and rebuild** again. Stuck on v0.3.1? Delete `mcla-recomp\out\build\win-amd64-release\CMakeFiles\mcla_recomp.dir\cmake_pch.hxx.pch` (only that file; the folder also holds your settings) and update again. ([#23](https://github.com/RenanQueiroz/mcla-recomp/issues/23)) |
| PowerShell says `running scripts is disabled on this system` | `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`, then run the script again. |
| The SDK build fails with `'crtversion.h' file not found` | Another Clang on your path was used. Update and run `make_pc.ps1` again: it now uses only its own. |
| Step 1 fails after downloading Clang, with `unable to run program "xz -d -qq"` | Windows 10's `tar.exe` cannot unpack `.tar.xz`. Update and run `make_pc.ps1` again: it now unpacks the archive with Python when `tar.exe` cannot. |
| Installing a tool fails with `No package found matching input criteria` | winget's package list on your PC is out of date or broken: run `winget source reset --force` in an administrator PowerShell, then `make_pc.ps1` again, or install that tool yourself (Python from python.org or the Microsoft Store works). |
| The SDK step fails with `Filename too long` or `'$GIT_DIR' too big`, or the build says FSR was left out | The folder's path is too long: git stops at 148 characters, and FidelityFX's shader compiler (FSR) at about 75, whatever Windows' long-path setting. Move the whole folder to a shorter path, for example `C:\Games\mcla-recomp`, and run the script again. |
| With `-Toolchain mingw`, the download "does not match its pinned SHA-256" | The file was damaged on the way or changed; it was deleted. Run the script again, or download `llvm-mingw-20250709-ucrt-x86_64.zip` from [llvm-mingw's release](https://github.com/mstorsjo/llvm-mingw/releases/tag/20250709), unpack it, and give the folder that holds `llvm-mingw-20250709-ucrt-x86_64` with `-ToolsDir`. |
| A game built with mingw says `libc++.dll` or `libunwind.dll` was not found | They belong next to `mcla.exe`: copy them from `tools\llvm-mingw-20250709-ucrt-x86_64\x86_64-w64-mingw32\bin`, or build again (the script copies them). |
| The build with mingw is silent about FSR, or says it is not available | FidelityFX's runtime does not build with llvm-mingw; see the [llvm-mingw section](building.md#without-microsofts-compiler-llvm-mingw). |
| `-SdkBundle` says the bundle is not this checkout's SDK, or has no `mcla-sdk-bundle.json` | It was made from other patches (or another SDK commit, or toolchain) than the ones checked out, usually before an update: take the bundle of the release this checkout is at, or build the SDK here (run without `-SdkBundle`). |
| The build slows the PC down or runs out of memory | Fewer compiler jobs: `$env:CMAKE_BUILD_PARALLEL_LEVEL = 4`, then run the script again (it caps them by free memory by itself, but only counts what is free at the start). |
| The SDK build fails with `no member named 'byteswap' in namespace 'std'` | Your Visual Studio is older than 2022 version 17.1 (VS 2019, or an early 2022). Update it in the Visual Studio Installer, or install Build Tools 2022, then run `make_pc.ps1` again. It now checks the version in step 1. |
| The SDK build fails inside a Windows SDK header (for example `xinput.h`, `expected function body after function declarator`) after installing a new Windows SDK | The SDK's build folder still had headers from the old Windows SDK. Update and run `make_pc.ps1` again: it now starts that folder again when the Windows SDK or Visual Studio changes. Or delete `third_party\rexglue-sdk\out\build` and run it again. |
| The SDK build fails with `unknown type name 'D3D12_FEATURE_DATA_D3D12_OPTIONS8'` | Your newest Windows SDK is 10.0.19041 or older. Update and run `make_pc.ps1` again: step 1 now installs Windows SDK 10.0.26100. Or add **Windows 11 SDK** to Build Tools 2022 in the Visual Studio Installer (Modify › Individual components). |
| The SDK configure fails with `could not open 'oldnames.lib'` | Clang picked a Visual Studio without the C++ tools (for example Visual Studio 2026 installed for something else) over the one that has them. Update and run `make_pc.ps1` again: it now points Clang at an install with the C++ tools. Or add **Desktop development with C++** to that Visual Studio in the Visual Studio Installer. |
| Step 2 fails with `config.h: No such file or directory` | The first download of the SDK was cut short. Update and run `make_pc.ps1` again: it now repairs the download. If it still fails, delete `third_party\rexglue-sdk` and run it again. |
| `codegen failed` | `game\default.xex` is missing or not the supported release; see the end of `out\codegen.log`. |
| After an update, the build says a patch has changed since it was applied, is in the SDK without a record, or does not apply | `.\launcher\build-game.ps1 -ResetSdk`, or the launcher's **More** → *Re-patch and rebuild the SDK*. |
| `no .NET 10 SDK found` | `winget install Microsoft.DotNet.SDK.10`, then `.\launcher\build-launcher.ps1` again. |
| The game stays at 60 FPS or paces unevenly | Turn VSYNC off in the pause menu's DISPLAY (or remove `vsync = true` from `mcla.toml`). |
| The game doesn't start after you added options under *More mcla.exe options* | Check that none is given twice: an option given twice is an error. |
| Geometry or textures look stale | Try `--clear_memory_page_state=true`, then the switches in [Turning a change off](off-switches.md), and report what made the difference. |
| The launcher says *Shaders weren't prepared* | The game plays as before, compiling shaders as it meets them. The message says why, and `launcher\logs\prepare-shaders-*.log` (with the game's own log, `prepare-shaders-game.log`) has the details. *In use* (by a running game, or another program that has a storage file open, such as a backup): it's tried again at the next Play. *Access denied* (or another error): a file in `Documents\mcla\cache\shaders` is read-only, or your account can't write there; that isn't tried again at every Play, so fix it and use *Prepare shaders*. *This default.xex is not the one the shader pack was made for*: your game isn't [the supported release](../README.md#which-release-of-the-game). |
| The game runs at a few frames a second, or is choppy with audio hiccups, on a PC with integrated and dedicated graphics (a laptop above all) | Up to v0.1.3 the game ran on the first GPU Windows listed, which on many laptops is the integrated one (fork issues #1 and #15 are likely cases, not confirmed). Now it takes the GPU *Settings › System › Display › Graphics* gives `mcla.exe`, else the high-performance GPU, and says which in its log: start it with `--log_file=run.log --log_level=info` and look for the lines starting `GPU:` (every adapter with its number and video memory, Windows' setting for the exe, and `GPU: '<name>' (<why>)`) and `graphics API:`; if the name is not the card you expect, open an issue with those lines. On v0.1.3 or earlier: *Settings › System › Display › Graphics › Add desktop app › `mcla.exe` (the one in `out\build\win-amd64-release`) › Options › High performance* (Windows then lists that GPU first, which the old code takes), or put `d3d12_adapter = N` in `mcla.toml` (N counts from 0 in the order Windows lists the adapters; try 1, and the log's `DXGI adapter:` line names the one used), plus `vulkan_device = N` with *Graphics API* on Vulkan. `--mcla_prefer_dedicated_gpu=false` brings back the old choice. |
| The game closes by itself | Start it with `--log_file=run.log --log_level=info` (the file is written next to `mcla.exe`; **More** → *Open the game folder*) and open an issue with the end of that file (see [Missed functions](#missed-functions) for where). |

## Missed functions

If the game stops with `Call to invalid or unregistered function at guest address ...`, the recompiler missed a function that is only reached through a pointer. That is a gap in the recompilation, which is upstream's area: please open the issue on [holdmysocks/mcla-recomp](https://github.com/holdmysocks/mcla-recomp/issues) with that line (the fix is one entry in `config/runtime_discovered.toml`), and the fork takes the fix at its next sync. Problems with the fork's changes or the launcher, or anything that doesn't happen with upstream's build, go to the [fork's issues](https://github.com/RenanQueiroz/mcla-recomp/issues).
