# Installing, the launcher and updating

The short version is in the [README](../README.md#windows). This page has the details. Building from source, without the setup wizard, is in [building.md](building.md).

## MCLA-Setup.exe and the setup wizard

Download **`MCLA-Setup.exe`** from the [latest release](https://github.com/RenanQueiroz/mcla-recomp/releases/latest) and run it. It installs the launcher for your Windows user (no administrator prompt) in `%LOCALAPPDATA%\Programs\MCLA`, adds Start menu and desktop shortcuts and opens it. On a PC with no install the launcher starts a **setup wizard**: it asks for a folder and your disc image (or the extracted game), then downloads checked, pinned build tools (llvm-mingw, CMake, Ninja, MinGit and the prebuilt SDK, so no Visual Studio, Git or Python), clones this fork at the release's tag, translates and builds the game and prepares shaders, and opens the launcher. It needs the internet (or the files downloaded by hand, see [*If something goes wrong*](troubleshooting.md#if-something-goes-wrong)) and about 10 GB; the folder's path can be at most 129 characters, with only plain letters, digits, spaces, dots, dashes and underscores. How it works, its limits and its test tools are in `launcher/README.md`, "The setup wizard" and "The installer". The release also has the launcher as a zip (`MCLA-Launcher-<tag>-win-x64.zip`, the same folder, unpacked anywhere), which starts the same wizard.

## The exe is not signed

Releases are not signed with a code-signing certificate, and will not be. Windows SmartScreen therefore may stop `MCLA-Setup.exe` the first time with *Windows protected your PC* (*Microsoft Defender SmartScreen prevented an unrecognized app from starting*): click **More info**, then **Run anyway**. (It asks for the downloaded file; the launcher it unpacks and the game it builds on your PC are written by programs on your PC, so they should not ask again.) If your browser holds the download back as uncommon, choose **Keep** (Edge: the downloads list, `...`, **Keep**, **Show more**, **Keep anyway**), or right-click the file, **Properties**, tick **Unblock**. To check that the file is the one the release workflow built, compare `Get-FileHash .\MCLA-Setup.exe` with the release's `SHA256SUMS` or `release.json`, or run `gh attestation verify MCLA-Setup.exe -R RenanQueiroz/mcla-recomp`. Some antivirus programs distrust any new unsigned program that unpacks files and downloads compilers; if one removes it, nothing is lost: the source of everything is in this repository, and the sections below build the game by hand.

## The launcher

The setup wizard and the build commands in [building.md](building.md#with-the-launcher-recommended) both leave you with the launcher and its shortcut.

From then on the shortcut is the way in. The launcher opens on the game's settings, and **Play** starts `mcla.exe`. When it opens it checks this fork on GitHub; if there are new commits it lists them under *What's new* and offers **Update and rebuild**. Commits that change only the launcher or the documentation don't need a game rebuild; when an update changed the launcher itself, it offers **Restart to update the launcher**. The **More** menu has *Rebuild the game*, *Re-patch and rebuild the SDK*, *Run the build in a terminal*, *Prepare shaders*, the game folder and the build logs, and says how many of upstream's commits the fork hasn't taken yet. Keep the repository where it was built: the game data is read from `game\`.

The launcher also **prepares shaders**: after every build and update, and before Play whenever the game's record of its shader storage says the graphics driver was updated, the card, the API or the resolution changed, the shader pack changed, or the shader cache was deleted or reset (the status line says why, counts the shaders and pipelines, and the game starts when it's done; **Play now** starts it at once and **Stop** ends the preparation without starting the game, which adds the pack by itself when it starts). It runs `mcla.exe --mcla_prepare_shaders=true` with the game's settings: it adds what the game's shader storage lacks of the fork's shader pack, rebuilding those shaders from your own game files, has the graphics driver compile every stored pipeline for your API and resolution, and quits. Places, cars and races the pack covers then don't compile shaders when you first meet them (no objects missing for a moment). The game itself also adds what its storage lacks of the pack at every start, so a storage that was deleted or reset fills again even without the launcher. The pack holds no game data, only fingerprints and the pipeline descriptions the storage keeps anyway ([KNOWN-ISSUES.md](../KNOWN-ISSUES.md#shaders-prepared-before-the-first-start-and-kept-prepared-2026-10-17-the-pack-grown-and-stale-entries-retired-2026-10-25)). **More** › *Prepare shaders* runs it by hand, and also tries again a pack whose import was turned off after it stopped the game's start twice, and the shaders that couldn't be rebuilt.

The launcher's settings are described in [settings.md](settings.md).

## Updating

The launcher's **Update and rebuild** does it all. From a terminal, `.\launcher\build-game.ps1 -Update` does the same: it fast-forwards to the fork's latest commit, keeping local changes (codegen rewrites `mcla_manifest.toml` and `generated\rexglue.cmake` with LF line endings; in a checkout made before `.gitattributes` asked for those they show as modified, and `git pull` can refuse to update them: `git add mcla_manifest.toml generated\rexglue.cmake` once, with nothing else changed in them, clears that); it patches the SDK afresh when the update changed anything in `patches\`, and builds.

An install made by the **setup wizard** follows the fork's releases instead of `main` (its launcher says so under *More*): **Update and rebuild** fetches the newest release's tag, downloads the SDK and tools the release names when they changed, rebuilds only what changed and prepares the shaders again when the game changed; a newer launcher in the release is announced with a link to its page. *More > Latest changes (main, untested)* follows `main` instead, with the SDK the install has, and is refused when `main` changes the SDK. Your settings, saves and shader storage are kept. A clone like the one above is not touched by any of this.

By hand: `git pull`, then `.\scripts\make_pc.ps1` again. It adds new SDK patches to an SDK patched earlier, and records each patch it applies: if a patch has changed since it was applied to your SDK, the build stops and names it. Then run `.\launcher\build-game.ps1 -ResetSdk`: it resets the SDK checkout, patches it again and rebuilds it (incrementally), then builds the game.
